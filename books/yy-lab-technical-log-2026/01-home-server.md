から始まった自宅サーバー

1. すべては友達から始まった

2026年5月頃。

当時、友達が自宅サーバーを運用していた。

それを見た私は、こう思った。

「面白そうだな。俺もやってみるか」

幸い、家には使っていないPCが余っていた。

サーバー専用の高価な機材を購入しなくても、手元にあるPCを使えば、とりあえず試すことはできる。

そこで、友達にいろいろ教えてもらいながら、自分でもWebサーバーを構築してみることにした。

この時点では、Kubernetesもクラスタも関係ない。

単純に、余っているPCでWebサイトを動かしてみたかっただけである。

まさか数か月後、分散システムの障害対応をすることになるとは思ってもいなかった。

2. 最初はApacheのWebサーバーだった

最初に使用したOSは、Ubuntu 26.04 LTS。

WebサーバーソフトウェアにはApache HTTP Serverを採用した。

構成は非常にシンプルだった。

余っていたPC
└── Ubuntu 26.04 LTS
    └── Apache HTTP Server
            └── Webサイト

            Ubuntuはサーバー用途でも広く利用されているLinuxディストリビューションであり、LTS（Long Term Support）版は長期的な保守を前提としている。

            Apacheも長い歴史を持つWebサーバーソフトウェアだ。

            ただし、当時の私がこれらのソフトウェアを選んだ理由について、今の知識で勝手に格好よく説明するつもりはない。

            最初は友達に教えてもらいながら、少しずつ環境を構築していった。

            Webサーバーが動く。

            自分で用意したPCからWebサイトを配信できる。

            それだけでも、なかなか面白かった。

            しかし、しばらく運用していると、次の疑問が湧いてきた。

            3. これ以上、何を強くできるんだろう？

            あるとき、私はAIに相談してみた。

            「これ以上、何を強くできる？」

            Webサーバーは動いている。

            しかし、せっかく自宅にサーバーを構築したのだから、もっといろいろ試してみたい。

            そこでAIから提案された技術の一つが、k3sだった。

            k3sとは

            k3sは、軽量なKubernetesディストリビューションである。

            Kubernetesは、コンテナ化されたアプリケーションの配置や実行状態を管理するためのシステムだ。

            複数のPCをクラスタとして扱い、その上でコンテナを動かすことができる。

            例えば、各PCへ個別にログインしてアプリケーションを起動する代わりに、Kubernetesへアプリケーションの望ましい状態を宣言し、管理させることができる。

            k3sは、比較的小規模な環境でもKubernetesを扱いやすくするための選択肢の一つだ。

            なるほど、そんなものがあるのか。

            そして、私は手元の機材について考えた。

            「そういえば、PCが3台余ってるな」

            ……じゃあ、やってみるか。

            導入理由は、ほぼこれである。

            業務システムの要件があったわけでも、大量のアクセスを処理する必要があったわけでもない。

            単純に面白そうだった。

            そして、ちょうど試せる機材があった。

            こうして、私の自宅サーバーは単一PCのWebサーバーから、複数台のPCを利用するクラスタへと発展していくことになった。

            4. ApacheからNginxへ

            k3sを導入するタイミングで、Webサーバーの構成も変更した。

            それまで使用していたApacheから、Nginxへ移行したのである。

            ただし、Ubuntu上に直接Nginxをインストールしたわけではない。

            Nginxはk3s上のコンテナとして動かす構成にした。

            ここは、単にWebサーバーソフトウェアを入れ替えただけではない。

            Webサーバーを動かす基盤そのものが変わったのである。

            移行前

            PC
            └── Ubuntu 26.04 LTS
                └── Apache
                        └── Webサイト

                        移行後

                        PC × 3台
                        └── k3sクラスタ
                            └── Nginxコンテナ
                                    └── Webサイト

                                    なお、ここでのNginxは通常のWebサーバーとして使用していた。

                                    Nginx Ingress Controllerとして利用していたわけではない。

                                    また、上の図は構成を簡略化したものであり、Nginxコンテナが常に複数ノードで動いていたことを意味するものではない。

                                    コンテナ化によって変わったこと

                                    コンテナを利用すると、アプリケーションとその実行環境をまとめて扱いやすくなる。

                                    さらにKubernetesでは、Podなどのリソースを使ってアプリケーションの実行状態を管理できる。

                                    例えば、Podが異常終了した場合、設定に応じてコンテナの再起動やPodの再作成が行われる。

                                    しかし、これだけでWebサイトが完全に無停止になるわけではない。

                                    ノードが停止した場合の再配置、通信経路、永続データの保存先など、別途考える必要がある。

                                    このあたりは、実際に運用してみると意外に奥が深かった。

                                    5. PCが3台あれば高可用性になるのか？

                                    結論から言うと、PCを3台並べるだけでは高可用性にはならない。

                                    複数のノードを用意しても、クラスタの管理機能が1台に集中していれば、そのノードが停止したときに管理機能へ影響が出る。

                                    また、WebサーバーのPodが1つしか存在しない場合、障害時にサービスが一時的に利用できなくなる可能性もある。

                                    ストレージも同様だ。

                                    ノードが3台あることと、保存したデータが3台に冗長化されていることは別の話である。

                                    つまり、考えるべきことは大きく分けて次のようになる。

                                    - Control Plane： クラスタの管理機能をどう維持するか
                                    - ワークロード： アプリケーションをどこで動かし、障害時にどう復旧するか
                                    - ネットワーク： ノードやサービス間の通信をどう確保するか
                                    - ストレージ： 保存したデータをどう保護するか

                                    単一PCでWebサーバーを動かしていた頃と比べると、考えることが一気に増えた。

                                    もっとも、最初からこれらを完全に理解していたわけではない。

                                    実際に構築して、問題が発生して、その都度調べていくことになった。

                                    6. embedded etcdによる3ノードHA構成

                                    現在の環境では、k3sのembedded etcdを利用し、3台のControl PlaneノードによるHA構成を採用している。

                                    etcdは、Kubernetesクラスタの状態に関する重要な情報を保存する分散Key-Valueストアである。

                                    クラスタの状態を複数のメンバー間で整合させるため、etcdはRaftという合意アルゴリズムを使用する。

                                    ここで重要になるのが、**クォーラム（過半数）**という考え方だ。

                                    3メンバー構成の場合、過半数にあたる2メンバーが正常に通信できる必要がある。

                                    正常なetcdメンバー数| クォーラム
                                    3台| 維持できる
                                    2台| 維持できる
                                    1台| 維持できない

                                    このため、3メンバー構成では、通常1台のメンバーが停止してもクォーラムを維持できる。

                                    一方、2台が停止すると過半数を失う。

                                    ここで注意したいのは、etcdの高可用性とWebサービスの高可用性は別物だということ。

                                    etcdが正常でも、アプリケーションのPodやネットワーク、ストレージに問題があれば、サービスは利用できなくなる。

                                    HA構成は万能ではない。

                                    障害に強い環境を作るには、それぞれの層を考える必要がある。

                                    7. そして障害対応が始まった

                                    クラスタを構築した後も、当然ながら問題は発生した。

                                    例えば、k3sのKubernetes API Serverが503エラーを返したことがある。

                                    また、etcdのリーダー選出やメンバー間通信を調べたり、データベースのデフラグを実施したりしたこともあった。

                                    Webサーバーを1台で動かしていた頃なら、まずそのPCとApacheの状態を確認すればよかった。

                                    しかし、k3sでは調査対象が増える。

                                    ノード自体は正常なのか。

                                    ノード間のネットワークは正常なのか。

                                    etcdはクォーラムを維持しているのか。

                                    API Serverは応答しているのか。

                                    Podは正常に起動しているのか。

                                    問題が発生した際には、これらを切り分けなければならない。

                                    最初は単にWebサイトを動かしたかっただけなのに、いつの間にか分散システムの障害対応をするようになっていた。

                                    どうしてこうなった。

                                    とはいえ、このような障害対応も、実際にシステムの仕組みを理解するための重要な経験になった。

                                    正常に動いているときには意識しない部分も、問題が起きると調べざるを得なくなる。

                                    そして、その過程で少しずつ理解が深まっていった。

                                    ※具体的な障害の原因、ログ、復旧操作については、当時の記録を照合したうえで別途追記する。

                                    8. 現在の自宅クラウド

                                    こうして、最初はApacheを動かすだけだった自宅サーバーが、k3sによる3ノードHAクラスタへと発展した。

                                    現在は、embedded etcdによるクラスタ管理に加え、Cloudflare Tunnelなどを組み合わせて各種サービスを運用している。

                                    また、バックアップやSSHの保護、障害発生時の復旧についても、構築当初より意識するようになった。

                                    もちろん、これはあくまで個人の実験環境である。

                                    商用クラウドのようなSLAを提供しているわけではないし、障害が発生することもある。

                                    それでも、自分で構築した環境には大きな利点がある。

                                    設定を変更できる。

                                    動作を観察できる。

                                    問題が起きたら、ログを確認して原因を調べられる。

                                    そして、必要であれば構成そのものを作り直すこともできる。

                                    最初から完成形を設計していたわけではない。

                                    友達のサーバーを見て興味を持ち、余っていたPCにUbuntuを入れ、ApacheでWebサーバーを立てた。

                                    さらに何かできないかとAIに相談したら、k3sを提案された。

                                    ちょうどPCが3台余っていたので、試してみた。

                                    その結果、今の自宅クラウドがある。

                                    始まりは「面白そうだからやってみるか」だった。

                                    今も基本的には、その延長線上で動いている。

                                    使用したPC

                                    k3sクラスタの構築には、家に余っていた3台のPCを使用した。

                                    構成は以下のとおり。

                                    ノード名| CPU| メモリ| ストレージ
                                    master ("yy")| Intel Core i5-4590| 8GB| 256GB SSD
                                    worker1| Intel Core i3-2350M| 10GB| 256GB SSD
                                    worker2| Intel Celeron 3855U| 8GB| 456GB SSD

                                    3台合計でメモリ26GB、ストレージの公称容量は968GBとなる。

                                    CPUの世代も性能もバラバラである。

                                    特にCore i3-2350Mは第2世代Coreプロセッサーで、かなり古い。

                                    しかし、今回の目的は最新の高性能サーバーを構築することではない。

                                    手元にある機材で、どこまでできるか試してみることだった。

                                    なお、ここで示したのは現在のストレージ構成であり、当初はHDDを搭載していたノードもあった。その後、SSDへ交換している。

                                    また、"master"や"worker"というノード名を使用しているが、現在のk3sは3台のControl PlaneによるHA構成として運用している。

                                    つまり、名前が"worker1"だからといって、現在もWorker専用ノードという意味ではない。

                                    こうして見ると、統一されたサーバー機材とはほど遠い。

                                    それでも、3台を組み合わせてクラスタを構築できた。

                                    中古PC、意外とやれる。
