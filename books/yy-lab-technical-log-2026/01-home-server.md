から始まった自宅サーバー

1. すべては友達から始まった

2026年5月頃、友達が自宅サーバーを運用していた。それを見た私は、「面白そうだな。俺もやってみるか」と思った。

幸い、家には使っていないPCが余っていた。サーバー専用の高価な機材を購入しなくても、手元のPCを使えば試すことはできる。そこで友達にいろいろ教えてもらいながら、自分でもWebサーバーを構築することにした。

この時点では、Kubernetesもクラスタも関係ない。単純に、余っていたPCでWebサイトを動かしてみたかっただけである。まさか数か月後、分散システムの障害対応をすることになるとは思ってもいなかった。

2. 最初はApacheのWebサーバーだった

最初に使用したOSはUbuntu 26.04 LTS。WebサーバーソフトウェアにはApache HTTP Serverを採用した。構成は非常にシンプルで、1台のPCにUbuntuをインストールし、その上でApacheを動かすというものだった。

Ubuntuはサーバー用途でも広く利用されているLinuxディストリビューションであり、LTS（Long Term Support）版は長期的な保守を前提としている。Apacheも長い歴史を持つWebサーバーソフトウェアだ。ただし、当時の私がこれらを選んだ理由について、今の知識で勝手に格好よく説明するつもりはない。

最初は友達に教えてもらいながら、少しずつ環境を構築していった。Webサーバーが動き、自分で用意したPCからWebサイトを配信できる。それだけでもなかなか面白かった。

しかし、しばらく運用していると、次の疑問が湧いてきた。「これ以上、何を強くできるんだろう？」

3. AIに聞いたらk3sを勧められた

そこで私はAIに相談してみた。Webサーバーは動いているが、せっかく自宅にサーバーを構築したのだから、もっといろいろ試してみたい。そんな中でAIから提案された技術の一つが、k3sだった。

k3sとは

k3sは、軽量なKubernetesディストリビューションである。Kubernetesはコンテナ化されたアプリケーションの配置や実行状態を管理するためのシステムで、複数のPCをクラスタとして扱い、その上でコンテナを動かすことができる。

例えば、各PCへ個別にログインしてアプリケーションを起動する代わりに、Kubernetesへアプリケーションの望ましい状態を宣言し、管理させることができる。k3sは、比較的小規模な環境でもKubernetesを扱いやすくするための選択肢の一つだ。

なるほど、そんなものがあるのか。そして私は、手元の機材について考えた。

「そういえば、PCが3台余ってるな」

……じゃあ、やってみるか。

導入理由は、ほぼこれである。業務システムの要件があったわけでも、大量のアクセスを処理する必要があったわけでもない。単純に面白そうだった。そして、ちょうど試せる機材があった。

こうして、自宅サーバーは単一PCのWebサーバーから、複数台のPCを利用するクラスタへと発展していくことになった。

4. 使用したPC

k3sクラスタには、家に余っていた3台のPCを使用した。現在のハードウェア構成は以下のとおりである。

ノード名| CPU| メモリ| ストレージ
master ("yy")| Intel Core i5-4590| 8GB| 256GB SSD
worker1| Intel Core i3-2350M| 10GB| 256GB SSD
worker2| Intel Celeron 3855U| 8GB| 456GB SSD

3台合計でメモリは26GB、SSDの公称容量は968GBとなる。ただし、これは単純な合計であり、OSが使用する領域やストレージの冗長化による実効容量の減少は考慮していない。

CPUの世代も性能もバラバラである。特にCore i3-2350Mは第2世代Coreプロセッサーで、かなり古い。それでも、今回の目的は最新の高性能サーバーを構築することではない。手元にある機材を使って、どこまでできるのか試すことだった。

なお、ここに記載したストレージは現在の構成である。当初はHDDを搭載していたノードもあったが、その後SSDへ交換した。

ノード名には"master"や"worker"という名前が残っているが、現在は3台ともControl Planeを担当するHA構成となっている。名前と現在の役割が一致しているとは限らないので注意してほしい。

5. ApacheからNginxへ

k3sを導入するタイミングで、Webサーバーの構成も変更した。それまで使用していたApacheからNginxへ移行したのである。

ただし、Ubuntu上に直接Nginxをインストールしたわけではない。Nginxはk3s上のコンテナとして動かす構成にした。つまり、単にWebサーバーソフトウェアを入れ替えただけではなく、Webサーバーを動かす基盤そのものが変わったことになる。

移行前は、1台のPCでUbuntu上のApacheがWebサイトを配信していた。移行後は、3台のPCで構成したk3sクラスタ上でNginxコンテナを動かし、Webサイトを配信するようになった。

なお、ここでのNginxは通常のWebサーバーとして使用していたものであり、Nginx Ingress Controllerではない。また、クラスタが3台構成だからといって、NginxのPodが常に3台へ分散配置されていたという意味でもない。

コンテナ化によって変わったこと

コンテナを利用すると、アプリケーションとその実行環境をまとめて扱いやすくなる。さらにKubernetesでは、Podなどのリソースを使ってアプリケーションの実行状態を管理できる。

例えば、Podが異常終了した場合、設定に応じてコンテナの再起動やPodの再作成が行われる。しかし、これだけでWebサイトが完全に無停止になるわけではない。ノードが停止した場合の再配置、通信経路、永続データの保存先などは、別途考える必要がある。

当時は、Webサーバーをコンテナ上で動かすだけでも新しい経験だった。それが後になって、クラスタ全体の可用性について考えるきっかけにもなった。

6. 最初は単一Control Planeだった

k3sを導入した当初、Control Planeは1台だけだった。3台のPCを利用してはいたものの、クラスタの管理機能まで冗長化されていたわけではない。

Control Planeは、Kubernetes API Serverやスケジューラなど、クラスタを管理する重要な機能を担当する。単一Control Plane構成では、そのノードが停止するとクラスタの管理機能に支障が出る。

既に動作しているコンテナが直ちにすべて停止するとは限らないが、新しいPodの配置やクラスタの状態変更などには影響が生じる可能性がある。

それでも、当初の目的であった「余っているPCでk3sを動かしてみる」という点では、十分に面白い環境だった。

しかし、ここでまた例の考えが浮かんできた。

「もっと強くできないかな？」

最初のWebサーバーからk3sへ移行したときと、ほとんど同じ動機である。

そして今度は、Control Planeを冗長化することにした。障害が発生してどうしても必要になったというより、さらに強い構成を試してみたかったのである。

7. embedded etcdによる3ノードHA構成

現在は、k3sのembedded etcdを利用して、3台のControl PlaneによるHA構成を運用している。

etcdは、Kubernetesクラスタの状態に関する重要な情報を保存する分散Key-Valueストアである。複数のメンバー間でデータの整合性を維持するために、Raftという合意アルゴリズムを使用する。

ここで重要なのが、クォーラム（過半数）という考え方だ。3メンバー構成のetcdでは、過半数にあたる2メンバーが正常に通信できる必要がある。

正常なetcdメンバー数| クォーラム
3台| 維持できる
2台| 維持できる
1台| 維持できない

このため、3メンバー構成では通常、1台のメンバーが停止してもクォーラムを維持できる。一方、2台が停止すると過半数を失い、正常な合意形成ができなくなる。

ただし、etcdの高可用性とWebサービスの高可用性は別物である。etcdが正常でも、アプリケーションのPod、ネットワーク、ストレージなどに問題があれば、サービスは利用できなくなる。

つまり、Control Planeを3台にしただけで、クラスタ上のすべてのサービスが無停止になるわけではない。

それでも、単一Control Plane構成から一歩進み、クラスタ管理機能の冗長性を確保できる構成になった。

8. クラスタを構築したら障害対応が始まった

クラスタを構築した後も、当然ながら問題は発生した。例えば、k3sのKubernetes API Serverが503エラーを返したことがある。また、etcdの状態を調べたり、デフラグを実施したりする場面もあった。

Webサーバーを1台で動かしていた頃なら、まずそのPCとApacheの状態を確認すればよかった。しかし、k3sでは調査対象が増える。ノード自体は正常なのか、ノード間のネットワークは正常なのか、etcdはクォーラムを維持しているのか、API Serverは応答しているのか、Podは正常に起動しているのか。問題が発生した際には、こうした点を切り分けなければならない。

最初は単にWebサイトを動かしたかっただけなのに、いつの間にか分散システムの障害対応をするようになっていた。

どうしてこうなった。

とはいえ、このような障害対応も、システムの仕組みを理解するための経験になった。正常に動いているときには意識しない部分も、問題が起きると調べざるを得なくなる。

具体的な障害原因や復旧操作については、当時のログを確認しながら別途整理する予定である。

9. 現在の自宅クラウド

最初はApacheを動かすだけだった自宅サーバーも、現在はk3sによる3ノードHAクラスタへと発展している。

embedded etcdによるクラスタ管理に加え、Cloudflare Tunnelなどを組み合わせて各種サービスを運用している。また、バックアップ、SSHの保護、障害発生時の復旧についても、構築当初より意識するようになった。

もちろん、これは個人の実験環境であり、商用クラウドのようなSLAを提供しているわけではない。障害が発生することもあれば、構成を変更することもある。

それでも、自分で構築した環境には面白さがある。設定を変更できるし、動作を観察できる。問題が起きたらログを確認して原因を調べ、必要であれば構成そのものを作り直すこともできる。

振り返ってみると、最初から完成形を設計していたわけではなかった。友達のサーバーを見て興味を持ち、余っていたPCにUbuntuを入れ、ApacheでWebサーバーを立てた。さらに何かできないかとAIに相談したらk3sを提案され、ちょうどPCが3台余っていたので試してみた。その後も、もっと強くしたいという理由でControl Planeを冗長化した。

面白そうだから始めた。PCが余っていたから試した。もっと強くしたくなったから構成を変えた。

今の自宅クラウドは、その積み重ねでできている。
